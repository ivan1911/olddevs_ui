# SplitPanel

## Кратко для AI

`SplitPanel` — две области с изменяемой границей: содержимое и панель деталей. Ось `position` (`side` / `bottom`) меняет направление раскладки. Размер управляемый через `size` + `onSizeChange` либо неуправляемый от `defaultSize`; хранение размера между сеансами — дело потребителя. На узком экране панель схлопывается пропом `collapsed`, а ширину даёт хук `useMediaQuery` из того же пакета.

## Когда использовать

- Экран «список слева, детали справа»: выбранная строка раскрывается рядом, а не на другой странице.
- Инспектор под таблицей: журнал, диагностика, предпросмотр запроса.
- Пользователю нужно самому решать, чему отдать место.

## Когда не использовать

- Детали открываются поверх содержимого и требуют внимания — это `Drawer` или `Dialog`.
- Область деталей фиксирована и не меняется пользователем — это обычная сетка из двух колонок.
- Нужна колонка навигации приложения — это `SideNav` внутри `AppShell`.

## Минимальный пример

```tsx
<SplitPanel aria-label="Детали заказа" panel={<OrderDetails id={selected} />}>
  <OrdersTable onSelect={setSelected} />
</SplitPanel>
```

## Public API

- `position`: `side` (по умолчанию) — панель справа, пользователь меняет её ширину; `bottom` — панель снизу, пользователь меняет высоту.
- `size` + `onSizeChange` — управляемый размер в пикселях; `defaultSize` — начальный, когда `size` не передан.
- `onSizeChange` зовётся **на каждом кадре** перетаскивания, но только когда значение действительно изменилось: тяга за границу зажимается в то же число и молчит. Если размер пишется в адрес страницы или на сервер, каждый кадр туда не нужен: throttle или запись по `pointerup` — забота потребителя.
- `defaultSize` читается **один раз, при монтировании**: смена пропа потом стартовый размер не двигает, иначе панель прыгала бы под пользователем от перерисовки родителя. Двойной щелчок по-прежнему возвращает к текущему значению `defaultSize`.
- `minSize` и `maxSize` — границы в пикселях. Размер зажимается ими и при перетаскивании, и при передаче пропом. Сужение границ на лету исправляет показанный размер, но `onSizeChange` не зовёт: событие без действия пользователя выглядело бы как правка состояния потребителя не по его воле. Перевёрнутый диапазон (`minSize > maxSize`) ничего не ломает — верхняя граница поднимается до нижней.
- `collapsed` схлопывает панель, **не размонтируя** её содержимое. Схлопывание посреди перетаскивания прекращает тягу: иначе состояние пережило бы исчезнувшую ручку, и наведение на новую двигало бы границу без нажатия.
- Адаптивного режима у компонента **нет**: на узком экране панель схлопывает `collapsed={!wide}`, где `wide` даёт `useMediaQuery` — см. «Узкий экран» ниже.
- `aria-label` даёт панели имя; без него она не объявляется областью.
- `className` ложится на внешний контейнер.

## Узкий экран: `collapsed` и `useMediaQuery`

Две области в ряд требуют места: на экране уже 1024 px (брейкпоинт `lg`) панель сбоку сжимает содержимое.
Что должно быть вместо неё — решает экран, а не компонент: просто одна область;
детали в `Drawer` по кнопке; список и сообщение «по одному» (почтовый клиент).
Проп `SplitPanel`, схлопывающий панель на узкой ширине, покрыл бы только первое,
поэтому штатный путь другой: компонент уже умеет `collapsed`, а ширину
даёт публичный хук.

```tsx
import { SplitPanel, useMediaQuery } from "@olddevs/ui";

const wide = useMediaQuery("(min-width: 1024px)"); // брейкпоинт `lg` Tailwind

<SplitPanel aria-label="Детали заказа" collapsed={!wide} panel={<OrderDetails id={selected} />}>
  <OrdersTable onSelect={setSelected} />
</SplitPanel>;
```

`useMediaQuery(query, serverValue = false)` возвращает, выполняется ли
медиазапрос сейчас, и перерисовывает компонент, когда это меняется. Запрос —
обычная строка CSS; брейкпоинты кита — штатные Tailwind 4: `sm` 640 px, `md`
768 px, `lg` 1024 px, `xl` 1280 px.

- **Что показывается до гидратации.** Сервер ширины не знает. Хук отдаёт
  `serverValue`, по умолчанию `false`: для запроса `min-width` это «узко», то
  есть mobile-first, как у самого Tailwind. На сервере и в первом кадре
  клиента панель схлопнута. React при гидратации сам берёт серверное значение
  и сразу после подставляет настоящее — **без ошибки расхождения**, но с одной
  перерисовкой: на широком экране панель появляется после гидратации. Если почти
  все пользователи на широких экранах, `useMediaQuery(query, true)` меняет умолчание
  на противоположное (первый кадр «широко», на узком экране панель схлопывается
  после гидратации). Выбор — за потребителем: кит не знает, какой случай вероятнее.
- **Нет `matchMedia`** (jsdom, старый браузер) — хук тоже отдаёт `serverValue`
  и не бросает.
- **Это не способ раскладывать страницу.** Показать или спрятать блок по ширине
  надо Tailwind-классом (`hidden lg:block`): класс работает с первого кадра и
  на сервере без перерисовки
  (ADR-0018). Хук нужен,
  когда от ширины зависит состав или поведение: что смонтировать, закрывать ли
  ящик, сколько месяцев показать.
- `collapsed` не размонтирует содержимое панели: форма и прокрутка внутри
  переживают переход «широко ↔ узко». Фокус, стоявший в панели, при схлопывании
  уходит в содержимое.

Два рабочих шаблона:

```tsx
// Детали в ящике: панель схлопнута, ящик открывается по кнопке только на узком.
<SplitPanel collapsed={!wide} panel={details}>{list}</SplitPanel>
<Drawer title="Детали" open={drawerOpen && !wide} onClose={() => setDrawerOpen(false)}>{details}</Drawer>

// Одна область за раз: на узком экране SplitPanel не монтируется вовсе.
{wide ? <SplitPanel panel={message}>{list}</SplitPanel> : reading ? message : list}
```

## Размер живёт у потребителя

Панель умеет помнить размер сама, но только пока смонтирована. Хранение между
сеансами (адрес страницы, профиль пользователя) остаётся за потребителем: у него состояние уже
где-то лежит, и второе хранилище внутри кита разошлось бы с первым молча. То же
разделение, что у состояния таблицы (ADR-0023).

При управляемом размере компонент **не пишет значение себе**: он сообщает
намерение через `onSizeChange` и показывает размер, который потребитель передал в `size`. Два
источника правды разошлись бы ровно на том кадре, где потребитель отклонит
значение.

## Почему ручка — настоящий ползунок

Универсального компонента для изменения размера react-aria не даёт: `ColumnResizer` и
`ResizableTableContainer`, которые работают в `Table`, привязаны к таблице.
Взята их модель — видимая полоса плюс скрытый `input[type=range]`.

Ползунок платформы приносит с собой всё, что иначе пишется руками и забывается
по частям: роль, объявление значения и границ, шаг, повтор при удержании,
поддержку скринридеров на сенсорном экране. `div` с `role="separator"` и
обработчиком стрелок повторяет это в лучшем случае наполовину.

**Значение ползунка — размер панели, а не координата границы.** Поэтому стрелка
вправо всегда увеличивает панель, хотя граница при этом уезжает влево: тянут
размер, а не разделитель.

## Клавиатура

- Ручка — обычный табстоп. Стрелки меняют размер шагом 16 px, со `Shift` — по одному пикселю, `Home` и `End` уводят ровно на границы.
- Шаг стрелки живёт в обработчике клавиш, а не в атрибуте `step`: шаговая база `input[type=range]` — это `min`, и `step=16` разрешил бы только значения `min + 16n`. Тогда `maxSize` не взялся бы с клавиатуры вовсе, а попиксельный результат тяги браузер молча округлял бы — объявленное значение разошлось бы с шириной панели.
- Двойной щелчок по ручке возвращает `defaultSize`. Клавиатурного пути к сбросу нет: нужный размер можно задать двумя способами, и второй (стрелки, `Home`, `End`) с клавиатуры работает.
- Нажатие на полосу переводит фокус на ползунок, поэтому сценарий «потянул мышью, дотяну стрелками» работает.
- Зона попадания у ручки шире видимой полосы: сама полоса 10 px, цель — 26 px; WCAG 2.5.8 требует не меньше 24 px.
- Пока тянут указателем, выделение текста в соседних областях выключено: иначе движение мимо полосы подсвечивает половину списка.

## Доступность и семантика

- Имя ручки приходит из каталога: с именем панели — «Изменить размер: Детали заказа» / Resize: Order details, без него — «Изменить размер панели» / Resize the panel. Ручек на экране бывает несколько, и одинаковое имя не помогает их различить.
- Текущий размер объявляется через `aria-valuetext` со склонением из локали.
- Обе области прокручиваемы и потому фокусируемы (`tabindex="0"`): до содержимого, которое прокручивается только указателем, `Tab` не доводит — правило axe `scrollable-region-focusable`. Схлопнутая панель из табуляции при этом выпадает вместе со всем остальным.
- Схлопнутая панель уходит из дерева доступности: если до панели доходит `Tab`, а самой её не видно, фокус теряется. Содержимое при этом остаётся смонтированным. Если фокус в момент схлопывания стоял внутри панели, он переводится в область содержимого (ручка при схлопывании исчезает) — иначе он оставался бы на скрытом узле и следующий `Tab` начинал обход с начала страницы.
- `--topbar-h` компонент не трогает (ADR-0016): он занимает данную ему область и наверх ни к чему не липнет.
